# S-1 Community isolation: design doc

## 1. Problem

A manager serves several HOAs from one company, and each HOA's tickets, documents and
announcements belong to that community alone (A-5, A-12). Today, privacy depends on nobody
forwarding a link (A-2). Every later story reads community data, so the boundary is built and
tested first. *Evidence IDs are assumptions until the interviews are logged; see backlog.md.*

## 2. Scope

Read-only API endpoints for tickets, Community-folder documents and announcements, all behind one
membership check. Bearer-token identification. A manager can work in every community they are
assigned to with one token.

## 3. Non-goals

- No sign-in, password or invitation flow; tokens are created by the seed script or by tests.
- No create, update or delete endpoints (S-2, S-3, S-5, S-6 add them).
- No Board Only documents and no file downloads (S-4).
- No web client; this story is the API service only.

## 4. Interface

All endpoints need the header `Authorization: Bearer <token>`. All IDs are path integers.

| Signature | Returns (200) | Errors |
|---|---|---|
| `GET /me/communities` | `list[Community]` that the caller is a member of, ordered by `id` | 401 |
| `GET /communities/{community_id}/tickets` | `list[Ticket]` (see rule R5), ordered by `id` | 401, 404 |
| `GET /tickets/{ticket_id}` | `Ticket` | 401, 404 |
| `GET /communities/{community_id}/documents` | `list[Document]`, folder `community` only | 401, 404 |
| `GET /documents/{document_id}` | `Document` (metadata only) | 401, 404 |
| `GET /communities/{community_id}/announcements` | `list[Announcement]`, newest `posted_at` first | 401, 404 |
| `GET /announcements/{announcement_id}` | `Announcement` | 401, 404 |

Python entry points: `app.main.create_app(db_path: str) -> fastapi.FastAPI` (creates the schema if
missing) and `app.access.require_member(conn: sqlite3.Connection, user_id: int, community_id: int) -> str`,
which returns the caller's role in that community or raises `NotFound`.

Error bodies, exactly: 401 → `{"detail": "Not authenticated"}`; 404 → `{"detail": "Not found"}`.

JSON shapes: `Community {id, name}`; `Ticket {id, community_id, created_by, title, category, status, created_at}`;
`Document {id, community_id, folder, title, uploaded_by, uploaded_at}`;
`Announcement {id, community_id, title, body, posted_by, posted_at}`.

## 5. Data (SQLite)

- `users`: `id` int PK ≥ 1; `display_name` text, 1–100 chars; `token` text, unique, ≥ 32 chars; `is_admin` int, 0 or 1.
- `communities`: `id` int PK ≥ 1; `name` text, 1–100 chars, unique.
- `memberships`: `user_id` int FK users; `community_id` int FK communities; `role` text, one of `resident`, `board`, `manager`; primary key (`user_id`, `community_id`).
- `tickets`: `id` int PK; `community_id` int FK; `created_by` int FK users; `title` text 1–200; `category` text 1–50; `status` text, one of `open`, `in_progress`, `resolved`; `created_at` text, ISO-8601 UTC.
- `documents`: `id` int PK; `community_id` int FK; `folder` text, `community` or `board_only`; `title` text 1–200; `uploaded_by` int FK users; `uploaded_at` text, ISO-8601 UTC.
- `announcements`: `id` int PK; `community_id` int FK; `title` text 1–200; `body` text 1–5000; `posted_by` int FK users; `posted_at` text, ISO-8601 UTC.

## 6. Rules

- **R1 (invariant).** In every 200 response, every item's `community_id` is a community the caller has a `memberships` row for.
- **R2 (precondition).** A request without a header, or with a token not in `users`, gets 401 with the exact body above, before any community data is read.
- **R3 (postcondition).** A request for a community, or an item in a community, where the caller has no membership gets 404 with a body byte-for-byte equal to the 404 for an ID that does not exist.
- **R4 (invariant).** No response from this story contains a document whose `folder` is `board_only`.
- **R5 (postcondition).** For a `manager`, the ticket list holds every ticket in the community. For a `resident` or `board` member, it holds exactly the tickets with `created_by` = caller, and `GET /tickets/{id}` on someone else's ticket gets 404.

## 7. Edge cases

1. An ID that exists in another community, and an ID that exists nowhere: same status, same body (R3).
2. A user who is `board` in A and `resident` in B: the role is taken per community, never globally.
3. A user with `is_admin` = 1 and no memberships: `/me/communities` returns `[]`; every community endpoint gets 404.
4. A header without the `Bearer ` prefix, an empty token, or a token with extra spaces: 401.
5. A non-integer ID in the path, such as `/tickets/abc`: FastAPI's 422, which carries no community data.

## 8. Decisions and open questions

Decisions:
- **D1.** "Outside your community" and "does not exist" answer the same 404, so a caller cannot learn that another community's item exists.
- **D2.** Identity is a bearer token stored on `users`. Sign-in arrives with a later story; the check stays in `app/auth.py`.
- **D3.** A role belongs to a (user, community) pair. `admin` is a flag on `users`, never a membership role.
- **D4.** Membership is decided only in `app.access.require_member`; endpoints never query `memberships` themselves.
- **D5.** Residents and board members see only their own tickets (R5). This is the narrowest rule, so widening it later cannot expose data that was hidden before.
- **D6.** The database path comes from the `COMMUNITYCONNECT_DB` environment variable (default `communityconnect.db`); tests pass a temporary path to `create_app`.

Open questions:
- **Q-3.** Should a management-company admin be able to read community tickets, documents and announcements? *Do not build anything that depends on this. Stop and ask.*
- **Q-5 / Q-7.** Should board members, or all residents, see other residents' tickets in their community? *Do not build anything that depends on this. Stop and ask.*
