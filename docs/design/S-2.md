# S-2 Ticket status lifecycle: design doc

## 1. Problem

Residents ask the manager for updates because they cannot see where a request stands, and a
"fixed" problem can come back (A-6, A-7). A status that only moves through allowed steps, with a
visible history, answers "where is my request?" without a phone call. *Evidence IDs are assumptions
until the interviews are logged; see backlog.md.*

## 2. Scope

A manager moves a ticket Open → In progress → Resolved. The resident who submitted it sees each
change and its time. That resident can reopen a Resolved ticket within `REOPEN_WINDOW_DAYS`.
Every other change is refused, and the ticket stays as it was.

## 3. Non-goals

- No notifications (email or portal) when the status changes.
- No assignment of tickets to vendors or staff.
- No editing of a ticket's title, category or photo.
- No backward move by a manager (see Q-6).

## 4. Interface

Builds on S-1: same token header, same 401 and 404 bodies, same `require_member` check.

| Signature | Body | Returns | Errors |
|---|---|---|---|
| `POST /tickets/{ticket_id}/status` | `{"status": "in_progress" \| "resolved"}` | 200 `TicketWithHistory` | 401; 403 caller is not a manager of the ticket's community; 404 not a member, or ticket missing; 409 `{"detail": "Transition not allowed"}`; 422 unknown status value |
| `POST /tickets/{ticket_id}/reopen` | none | 200 `TicketWithHistory` | 401; 403 caller is not the ticket's `created_by`; 404; 409 `{"detail": "Transition not allowed"}` if status is not `resolved`; 409 `{"detail": "Reopen window has passed"}` |
| `GET /tickets/{ticket_id}` | n/a | 200 `TicketWithHistory` | as S-1 |

`TicketWithHistory` = S-1 `Ticket` plus `resolved_at: str | null` and `history: list[{from_status, to_status, changed_by, changed_at, kind}]`, oldest first.

Python: `create_app(db_path: str, clock: Callable[[], datetime] | None = None) -> FastAPI`; `clock` returns a timezone-aware UTC `datetime` and defaults to the system clock. `app.settings.REOPEN_WINDOW_DAYS: int`.

## 5. Data

- `tickets` (S-1) gains `resolved_at`: text, ISO-8601 UTC, or NULL. It is set exactly when `status` becomes `resolved` and cleared on reopen.
- `ticket_history`: `id` int PK; `ticket_id` int FK; `from_status`, `to_status` text, each one of `open`, `in_progress`, `resolved`; `changed_by` int FK users; `changed_at` text, ISO-8601 UTC; `kind` text, `advance` or `reopen`.
- `REOPEN_WINDOW_DAYS`: int ≥ 1, value pending Q-1 (placeholder in `app/settings.py`).

## 6. Rules

- **R1 (invariant).** The allowed transitions are exactly: `open→in_progress` (manager), `in_progress→resolved` (manager), `resolved→open` (creator, reopen). Any other request returns an error and leaves `status`, `resolved_at` and `ticket_history` unchanged.
- **R2 (invariant).** For every ticket, `history[i].to_status == history[i+1].from_status`, and the last entry's `to_status` equals `status` (or the history is empty and `status` is `open`).
- **R3 (invariant).** `resolved_at` is non-NULL if and only if `status` is `resolved`.
- **R4 (precondition).** A reopen succeeds only while `clock() < resolved_at + REOPEN_WINDOW_DAYS days`.
- **R5 (postcondition).** After a successful change, `GET /tickets/{id}` by the creator shows the new status and one new history entry with the caller's ID and `clock()` time.

## 7. Edge cases

1. A reopen at exactly `resolved_at + REOPEN_WINDOW_DAYS`: refused (R4 is strict).
2. Setting the status a ticket already has (`in_progress → in_progress`): 409, no history entry.
3. A board member, or another resident of the same community, trying to reopen: 403.
4. A manager who is also the ticket's creator: may advance it as manager and reopen it as creator.
5. Two managers advancing the same ticket at the same moment: only one history entry per transition.

## 8. Decisions and open questions

Decisions:
- **D1.** A reopen returns the ticket to `open`, not `in_progress`, so the manager has to start it again.
- **D2.** Wrong role → 403; wrong state → 409; checked in that order, after the S-1 membership check (404).
- **D3.** A reopen clears `resolved_at`; the next resolve sets a new one, and the window restarts from it.
- **D4.** Status changes run in a single SQLite transaction that re-reads `status` before writing, so concurrent requests cannot both succeed.

Open questions:
- **Q-1.** What value should `REOPEN_WINDOW_DAYS` have? *Do not build anything that depends on this. Stop and ask.* (Code and tests read the setting; no number is written anywhere else.)
- **Q-6.** Can a manager move a ticket backwards (In progress → Open)? *Do not build anything that depends on this. Stop and ask.*
